# 生产看板系统 · 设计方案

| 项目 | 内容 |
|---|---|
| 需求对接人 | 贾广现 |
| 展示环境 | 二楼生产车间 MAXHUB 大平板（安卓系统） |
| 部署环境 | 优先单体部署；备选 Windows Server 2012 |
| 文档状态 | 初稿，待需求确认后修订 |
| 更新日期 | 2026-07-27 |

---

## 一、项目目标

在车间大屏上实时呈现各产线生产进度，让班组长和车间管理人员**抬头就能看到当前状态**，不用再去问、去查、去翻表格。

具体要解决的问题：

1. 各产线当前完成了多少、离目标还差多少
2. 哪条线停了、哪条线在等料，异常能第一时间被看见
3. 全车间今日整体达成情况

## 二、需求现状

### 已明确

- 呈现生产进度
- 展示终端为二楼 MAXHUB 大平板（安卓）
- 部署尽量单体，否则用 Windows Server 2012

### 待确认（**这是当前最大的阻塞项**）

见文末「待确认事项清单」。其中**数据来源**直接决定工作量，差距可达数倍。

## 三、系统架构

### 整体结构

```
┌──────────────────────────────┐
│  MAXHUB 大屏（安卓 · 浏览器）  │
│  全屏常显，每 3 秒自动刷新     │
└──────────────┬───────────────┘
               │ ① HTTP 请求 /api/progress
               ▼
┌──────────────────────────────┐
│  看板服务（单进程）            │
│  · 托管前端页面                │
│  · 提供数据接口                │
│  · 数据格式转换 + 缓存         │
└──────────────┬───────────────┘
               │ ② 读取数据
               ▼
┌──────────────────────────────┐
│  数据源（MES / ERP / Excel）   │
└──────────────────────────────┘
```

### 为什么中间要有「看板服务」这一层

大屏能不能直接读 MES 数据库或调 MES 接口？技术上想得通，实际不行，原因有四：

| 问题 | 说明 |
|---|---|
| **跨域限制** | 浏览器安全机制，MES 接口多半没配置允许跨域，前端直连会被浏览器直接拦截 |
| **凭证泄露** | 数据库密码/Token 写在前端代码里，任何人打开大屏浏览器都能看到 |
| **冲击源系统** | 多块屏幕高频刷新会直接压到 MES 上，影响生产系统本身 |
| **数据格式** | MES 返回的原始结构不是看板要的形状，需要一层加工 |

看板服务这一层同时解决这四件事，并且让**数据源可替换**——将来从 Excel 换成数据库，只改这一层，前端一行不动。

### 单体部署如何满足

整套系统就是**一个进程 + 一个端口**：同一个服务既托管前端页面，也提供数据接口。不需要单独装 Web 服务器（IIS/Nginx），不需要单独的数据库（数据来自现有系统），符合「尽量单体部署」的要求。

原型已验证：两个文件、零第三方依赖、`node server.js` 一条命令启动。

## 四、数据来源方案对比

**这是需要贾广现确认的第一件事**，四种情况工作量差异很大：

| 方案 | 做法 | 工作量 | 主要风险 |
|---|---|---|---|
| **A. 直连 MES/ERP 数据库**（推荐） | 后端只读查询业务库 | 小 | 需 DBA 开只读账号；需要摸清表结构和字段含义 |
| **B. 调用现有接口**（推荐） | 后端定时调 MES 接口 | 小 | 需要接口文档和访问凭证；需确认接口频率限制 |
| **C. Excel 定期导入** | 监控指定目录，解析文件 | 中 | 依赖人工上传，一旦忘记上传看板就是旧数据 |
| **D. 系统内人工录入** | 需做录入界面 + 账号体系 + 数据库 | **大** | 性质变了：从「展示看板」变成「完整生产管理系统」，工期至少翻倍，且增加车间人员日常负担 |

**建议优先争取 A 或 B**。如果现场目前靠白板/纸质记录，落到 D 之前应先和贾广现确认：是否有必要一步到位，还是先用 C 过渡。

## 五、技术选型

### 前端（无争议）

原生 HTML + CSS + JavaScript，不引入框架。

理由：看板功能边界清晰（拉数据、渲染、刷新），引入 React/Vue 会带来构建工具链和依赖包，对单体部署和长期维护都是负担。原生方案零依赖、改一个文件就能上线。

**唯一风险**：MAXHUB 自带浏览器若为老版本 Chromium，可能不支持较新语法。应对方式见「风险」章节。

### 后端（取决于服务器版本）

Windows Server 2012 对运行时版本有硬性限制，必须先确认再定：

| 服务器实际版本 | 推荐方案 | 说明 |
|---|---|---|
| Server 2016 及以上 / 可换新机器 | **Node.js 20 LTS** | 首选。前后端同一种语言，维护成本最低 |
| Server 2012 **R2** | Node.js 16 或 18 | 可行，但属于已停止维护版本，存在安全隐患 |
| Server 2012（**非 R2**） | **.NET Framework 4.8** | Windows 原生支持，无需额外装运行时，最稳妥 |

**重要**：无论后端换成哪种语言，**前端页面完全不用改**——因为前端只依赖 `/api/progress` 这个接口约定，不关心后端用什么写的。这是前后端分离带来的实际好处。

## 六、看板内容设计

### 版面结构

```
┌───────────────────────────────────────────────────┐
│ 生产看板    白班                        14:27:39   │  标题栏
├───────────────────────────────────────────────────┤
│ ┌───────────┐ ┌────────┬────────┬───────┬───────┐ │
│ │ 今日总完成率│ │计划产量│实际产出│在产线数│异常线数│ │  核心指标
│ │   67.9%   │ │  6,000 │  4,073 │   3   │   2   │ │
│ └───────────┘ └────────┴────────┴───────┴───────┘ │
├───────────────────────────────────────────────────┤
│ 产线明细                                           │
│ 一号线·装配  ▶运行中   869/1,200  ▓▓▓▓▓▓░░░  72.4% │
│ 二号线·焊接  ▶运行中   745/  900  ▓▓▓▓▓▓▓░░  82.8% │  产线列表
│ 三号线·喷涂  ●已完成 1,500/1,500  ▓▓▓▓▓▓▓▓▓ 100.0% │
│ 四号线·总装  ◆待料     310/  800  ▓▓▓░░░░░░  38.8% │
│ 六号线·检测  ■停机     180/  600  ▓▓░░░░░░░  30.0% │
├───────────────────────────────────────────────────┤
│ 数据每 3 秒自动刷新 · 最后更新 14:27:39            │
└───────────────────────────────────────────────────┘
```

### 三条设计原则

**1. 只有一个主数字**

整块屏幕上字号最大的只能有一个（今日总完成率）。远距离扫一眼先抓到全局，再看细节。若多个数字都做成大字号，会互相抢注意力，反而什么都看不清。

**2. 状态不能只靠颜色区分**

每种状态配**不同形状**的图标加文字：

| 状态 | 图标 | 颜色 |
|---|---|---|
| 运行中 | ▶ | 蓝 |
| 已完成 | ● | 绿 |
| 待料 | ◆ | 黄 |
| 停机 | ■ | 红 |

原因：红绿色盲人群约占男性 8%，车间常用的「红黄绿灯」配色，这部分工人无法辨识。经配色验证工具实测，标准红与标准绿在红绿色盲视角下的差异值仅 4.1（安全阈值为 8），属于**不可辨识**。形状 + 文字才是可靠的识别通道，颜色只作为辅助。

**3. 数据过期必须显式报警**

看板最危险的场景不是崩溃黑屏——黑屏所有人都看得见。真正危险的是**服务已经挂了，屏幕还挂着两小时前的数字**，管理人员照着假数据做决策。

因此设计要求：连续 2 次拉取失败即弹出醒目提示，并明确写出「当前显示的是 X 秒前的旧数据」。

### 可选扩展（二期考虑）

- 分时产量趋势（小时柱状图）
- 停机时长排名 / TOP 异常原因
- 按当前速度预测能否达成日目标
- 产线数量超过一屏时分页轮播

## 七、接口设计

```
GET /api/progress
```

响应：

```json
{
  "updatedAt": "2026-07-27T06:27:39.000Z",
  "shift": "白班",
  "summary": {
    "totalPlan": 6000,
    "totalActual": 4073,
    "rate": 67.9,
    "running": 3,
    "abnormal": 2
  },
  "lines": [
    {
      "id": 1,
      "name": "一号线 · 装配",
      "plan": 1200,
      "actual": 869,
      "rate": 72.4,
      "status": "运行中"
    }
  ]
}
```

状态取值固定为四种：`运行中` / `已完成` / `待料` / `停机`。

**接口一旦定下，前后端就可以并行开发**——前端拿假数据先把页面做完，后端接真实数据源，两边互不阻塞。

### 刷新策略

采用**轮询**（每 3 秒请求一次），不用 WebSocket。

理由：生产进度秒级实时性没有意义（产量数字本来就是分钟级变化），轮询实现简单、断线自动恢复、不需要处理连接保活，长期无人值守场景下更可靠。

负载评估：6 条产线单次响应约 2 KB，每 3 秒一次 → 约 0.7 KB/s。即使 20 块大屏同时刷新也毫无压力。

## 八、部署方案

### 服务端

1. 部署包放在服务器固定目录（如 `D:\kanban\`）
2. **注册为 Windows 服务**（用 nssm 或 node-windows），实现：
   - 开机自动启动，不需要人工登录服务器
   - 进程意外退出时自动拉起
3. 开放内网端口（如 3000），配置防火墙规则

### MAXHUB 大屏

1. 安装新版 Chrome（不用自带浏览器，避免内核过旧）
2. 配置**开机自动启动浏览器**并打开看板地址
3. 浏览器设为**全屏 kiosk 模式**，隐藏地址栏和按钮，防止误触退出
4. 关闭屏保和自动休眠
5. 建议配置有线网络，Wi-Fi 在车间环境容易受干扰

### 无人值守要求

大屏是「装上去就不该再管」的设备，以下几点必须落实：

| 要求 | 措施 |
|---|---|
| 服务器重启后自动恢复 | 注册为 Windows 服务，设置自动启动 |
| 服务崩溃自动重启 | 服务恢复策略配置为失败后重启 |
| 大屏断电重启后自动显示 | 安卓开机自启动 + 浏览器 kiosk 模式 |
| 网络抖动自动恢复 | 前端轮询失败会持续重试，网络恢复后自动继续（已实现） |
| 数据异常可被发现 | 断连报警 + 数据过期提示（已实现） |

## 九、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **数据来源未确定** | 阻塞开发，无法估算工期 | **最高优先级**，需尽快与贾广现确认 |
| Server 2012 跑不了新版 Node | 技术选型推翻重来 | 先确认是否为 R2；确认不行则改用 .NET 4.8，前端不受影响 |
| MAXHUB 浏览器内核过旧 | 页面显示错乱或白屏 | 装新版 Chrome；实在不行则降级语法兼容 |
| MES 不开放数据库/接口权限 | 拿不到数据 | 退而求其次用 Excel 导入过渡 |
| 车间 Wi-Fi 不稳 | 看板频繁断连 | 优先接有线；前端已有断线重连与过期提示兜底 |
| 需求扩散为完整生产管理系统 | 工期不可控 | 明确一期只做「展示」，录入/排产等需求单独立项 |

## 十一、待确认事项清单

**建议直接拿这份清单去和贾广现、运维逐条对答案。**

### 数据相关（最高优先级）

1. 生产进度数据目前记录在哪里？MES / ERP / Excel / 纸质白板？
2. 若有系统，能否提供**只读数据库账号**或**接口文档**？
3. 「进度」的口径是什么？按件数、工时、还是工单完成比例？
4. 计划产量从哪来？是否每天/每班次会变？
5. 产线状态（运行/待料/停机）是系统里已有的字段，还是需要人工标注？

### 展示相关

6. 一共几条产线？需要同时显示全部，还是可以分页轮播？
7. 除了产量进度，还要不要显示：良品率、停机时长、异常原因、人员出勤？
8. 按班次统计还是按自然日？班次怎么划分？
9. 需要展示历史趋势吗（如近 7 天达成率）？

### 环境与部署相关

10. Windows Server 是 **2012** 还是 **2012 R2**？（决定技术选型）
11. 服务器能否安装新软件、开放端口？谁负责？
12. MAXHUB 型号、系统版本、自带浏览器版本？能否安装 Chrome？
13. 大屏走有线还是 Wi-Fi？能否访问到部署服务器？
14. 大屏是否 24 小时常开？夜班要不要显示？

### 其他

15. 看板是纯展示，还是需要触摸交互（点击查看明细、切换产线）？
16. 上线时间有没有硬性要求？
17. 后续谁负责日常维护？
